# Proposal: Assign Imported Lift History to Macrocycles

**Status:** `accepted`
**Date:** 2026-11-06
**Issue:** [#1170](https://github.com/merickvaughn/lifting-logbook/issues/1170)

---

## Problem

The Consistent Intermediate Lifter migrating off a spreadsheet brings history with started-and-dropped programs, breaks, restarts and runs that went long. The import wizard can't represent any of that: the lifter picks one program for the whole file, must supply macrocycle and workout numbers as columns, and nothing reads the dates. Imported history therefore can't serve job J3 (track progress within a session or block), and it weakens job J2 (know what weight to use next session), because the record a lifter looks back on is grouped wrongly or can't be imported at all.

## Proposed Solution

Add an Assign step between Review and Preview that groups imported lift history into macrocycles from its dates. It shows each stretch (a contiguous run of sessions the importer groups together) with its dates, the breaks around it and a suggested status, and the lifter can change any of them before commit. Rules produce the suggestions, so import works with no LLM configured. An optional LLM can add further suggestions, which count only if the lifter confirms them. Each confirmed stretch becomes a row in a new `macrocycle` table and shows up in a list of past macrocycles. A break of more than two weeks usually means starting over, so the rules suggest a new macrocycle there and never insist on one. The file's latest unfinished run can continue as the current macrocycle if the lifter chooses. Otherwise this classifies past history only. Training maxes and the live plan change only when the lifter chooses that for a run they're continuing. Nothing adjusts them automatically after a break, and no programming is generated beyond that run's remaining schedule, so this stays clear of the two matching non-goals in the product requirements document.

Re-importing a file adds nothing new, and the lifter can instead overwrite what's stored with a fresh import, clear their training data for a fresh start, and download any of it in a form this importer can read back. Overwrites and clears keep a backup for 30 days. A lifter can also record a non-cycle workout, which belongs to no program or macrocycle (decision 23).

In this proposal, a session is every row with one date.

### Rollout and revert

1. Piece 1 ships first, in two deploys. The first adds the table, stable ids, the write guards and clients that send the id, and it counts writes with no id. Numbers don't change yet, because migrations run while the last good API revision is still serving, and that revision doesn't check ids. The second runs the renumbering backfill and starts rejecting writes with no id. Piece 1 writes no imported rows, so its code can be reverted until piece 3 is on. Its backfill changes stored numbers, so reverting those takes the reversal script in decision 18.
2. Pieces 3, 6, 7 and 8 sit behind `IMPORT_ASSIGN_ENABLED`, off by default. With it off, the wizard shows the same steps and required columns as today, but piece 1 still changes how the file-number paths read those numbers (decision 2). It goes on in staging first, then production. Piece 7 is behind the flag because an exported file only round-trips through assigned imports.
3. Turning the flag off stops new assigned imports and leaves stored rows alone. That's the normal way back.
4. Reverting piece 1's code isn't safe once imported rows exist, because `prevNum + 1` can land on an imported number. Undo those batches first, or leave piece 1 in place.
5. Piece 9 has no flag, because a lifter who doesn't use it sees nothing change apart from one new action. Its Assign choice arrives with piece 3, behind that flag. Reverting piece 9's code leaves its rows stored and out of sight until it's back.

### Testing the LLM version

Testing uses local Ollama, because it's free and history never leaves the machine. A local model says little about a paid hosted one, so any verdict holds for the local model only, and choosing a production provider is a separate decision after the comparison. Ollama's OpenAI compatibility page confirms JSON mode but doesn't mention `json_schema`, so responses are validated regardless. The same page says its OpenAI API can't set the context size, so testing uses a Modelfile with a known `num_ctx`, and the pre-registration records prompt size against it. I haven't tested what Ollama does with an over-long prompt.

### Observability

- **Logs:** counts only, following `import.controller.ts:255`: sessions, stretches, flags, changes the lifter made to the suggestions, rows skipped as duplicates, the provider, duration, tokens and suggestions dropped by reason. Prompts and responses are never logged.
- **Spans:** one around the provider call, and a manual one around any raw SQL, which isn't auto-traced ([ADR-024](../adr/ADR-024-prisma-otel-sdk-override.md)). The lock in decision 13 is raw SQL.
- **Client errors:** the suggestion, Assign and commit calls report failures through `logClientError`, so a failed suggestion request doesn't vanish into the Unavailable state.
- **Failed batch saves:** the existing silent catch at `import.controller.ts:670-675` stays only for flag-off imports. For assigned imports the failure fails the commit (decision 17).
- **Renumbering:** a span around it, because it's raw SQL, with macrocycles renumbered, rows rewritten and duration. A write refused for a stale macrocycle id is counted, so stale pages show up in Grafana.
- **Destructive actions:** overwrite, clear, restore and backup deletion each log their scope and row counts, never the rows. A failed backup fails the action and logs why (decision 21).
- **Non-cycle workouts:** creating and deleting one log counts, never lifts or notes, and client writes report failures through `logClientError`.

## Resolved Design Decisions

The owner reviewed each of these on 2026-11-06. Decisions 2, 3, 5, 10, 11, 12 and 18 reflect changes from that review, and decisions 19 to 23 came out of it.

1. **A new `macrocycle` table holds the history.** Its columns are user, program, number, start date, a nullable end date, status (`completed`, `abandoned`, `overran`, `in-progress`, `unknown`), whether the lifter chose that status, origin (`imported`, `live`, `legacy`, `non-cycle`) and the unmatched flag from decision 9, with a unique key on user, program and number. `macrocycle_dashboard` stays the pointer to the current one. Live macrocycles get a row when they're created, with `macrocycleDate` as the start date. Starting the next one closes the previous row: its end date is its last record's date, and its status comes from decisions 6 and 7. An `in-progress` row whose last session is more than 14 days old reads as `abandoned`, so it can't go stale. That doesn't apply to the macrocycle the dashboard points at, which is still current after a long break, or to a status the lifter chose. Rejected: deriving macrocycles from `lift_record` dates alone, because status and an empty or unmatched stretch can't be stored or edited that way. Also rejected: widening `macrocycle_dashboard`, whose uniqueness is one row per user and program.
2. **Imported macrocycles are read-only history, unless the lifter continues the file's latest run.** Assign offers "Continue this as my current macrocycle" on the file's last stretch when it has a known program, workouts left, and a last session within 14 days of the import date. It's off until chosen. Choosing it replaces any status choice on that stretch: it's stored with origin `live` and status `in-progress`, and the stretch's status control is locked until the choice is undone. It also points `macrocycle_dashboard` at it, makes its program the active one as `POST switch` does, and schedules the remaining workouts from the next training day after the import date. Completed workouts get no schedule. If that program has a live macrocycle, Assign says how many sets it holds and asks to end it, and the run can't continue unless the lifter agrees. Ending it closes its row as starting the next one does (decision 1). The batch records the ended macrocycle by stable id, because its number can change. Undo reverses all of this, including any training max changed under decision 10, unless that max has since been changed, which is skipped and flagged as undo does today. Sets logged on the run since the import aren't part of the batch, so they stay. They become non-cycle workouts (decision 23), one per workout number, and the run's `macrocycle` row, schedule and overrides are removed. They no longer record the program they were logged under, which the owner accepted so that there's one kind of set outside a macrocycle. Undo is refused with a reason once the dashboard no longer points at the run, because something else has become current. Every other imported macrocycle never becomes current and never appears on live workout pages. `currentMacrocycleOrFirst` falls back to macrocycle 1 when a program has no dashboard, so workout and focus routes treat an imported number 1 as having no live records, and `PUT focus-state` writes nothing there.

    These writes reject an imported macrocycle or an unknown number with a 4xx, so its rows can't change training maxes or be edited one by one: `fromMacrocycleNum`, `POST lift-records`, `PATCH lift-records/:id`, `POST lift-records/import`, flag-off commits, the lift-override `POST` and `DELETE`, `PATCH .../reschedule`, the skip `POST` and `DELETE`, and `PUT focus-state`.

    The two import paths that take a number from a file, `POST lift-records/import` and flag-off commits, can't trust that number once stored numbers follow dates. So from piece 1 they use decision 13's count-based duplicate check, and a file number only groups rows. Its rows join the stored macrocycle with that number when their dates fall inside its dates, or after its start if it's the current one. Otherwise they form a new `legacy` macrocycle and the program renumbers. They never join an `imported` macrocycle.

    To correct imported history, undo the batch and import again: the past-macrocycles list offers Undo for the batches behind each imported macrocycle, through a new route that lists batches, since `batchId` otherwise lives only in the wizard. Deleting the current macrocycle removes `live` and `legacy` rows and their records, as Delete does today, and keeps `imported` ones, so history survives. Rejected: letting any older run become current, whose remaining workouts would be scheduled from today against stale maxes, and a later "Make current" action on the list, which needs a switch flow and makes undo much harder. Also rejected: limiting the offer to a program with no logged sets, because the owner wants to be able to end a live macrocycle for this. Also rejected: refusing undo once a set is logged, and deleting those sets on undo. The owner chose to keep them and allowed sets to stand apart from a macrocycle, which decision 23 provides. Also rejected: a null `macrocycleNum` for those sets, which would need every reader changed and wouldn't be protected by the unique key, since Postgres treats nulls as distinct.
3. **Numbers follow start date, by rewriting what's stored.** Within a user and program, macrocycles are numbered 1 to N in start-date order. Ties keep their current relative order, and a new macrocycle sorts after those it ties with, so an undo puts the original numbers back. Anything that adds or removes a macrocycle or moves its start date renumbers that program in the same transaction: commit, undo, overwrite, clear, restore, delete and the backfill. Most imports of newer history and every normal next macrocycle change nothing already stored, since the new one is last. An import of older history rewrites the number on `lift_record`, `macrocycle_dashboard`, `workout_date_override`, `workout_skip_override`, `workout_lift_override`, `focus_day_state`, `macrocycle_scheduled_workout` and `macrocycle`, for that program's macrocycles whose number changed, from one map of old to new numbers. The unique keys are checked per row, so the rewrite passes through a temporary offset. Deleting a macrocycle removes its rows from all these tables, so a later renumbering can't land on a leftover. Import batches identify assigned rows by `lift_record` id, which a rewrite doesn't change, and the rewrite updates the keys in older batches. It all runs under the lock in decision 13, and the unique key is the backstop: a conflict fails the write with a 409 and changes nothing.

    This means a live macrocycle's number and URLs can change. Workout pages read the current macrocycle whatever the URL says, then post with the URL's number, so an old bookmark shows one macrocycle and writes to another. To keep that from corrupting data, each `macrocycle` row has a stable id, returned with every macrocycle-scoped read, and three rules apply:

    - **Pages follow the number.** A workout page whose URL number isn't the one it read redirects to the right URL, so a reload can't loop.
    - **Every macrocycle-scoped write carries the id.** That's each route decision 2 lists, plus `PATCH lift-records/:id`, whose record id embeds the number. A stale record id could otherwise miss with a 404, or match the same workout, date, lift and set in another macrocycle. A write whose number no longer maps to its id gets a 409 with the code `macrocycle-moved`, and the page reloads. Once the renumbering step of Rollout is live, a write with no id gets a 400 asking for a reload. Those would be browser tabs open across the deploy: `apps/mobile` has no API client yet, so no other client exists.
    - **Every macrocycle-scoped write takes the decision 13 lock in shared mode, in its transaction.** It checks the id under that lock, so a rewrite can't commit between the check and the write. One that can't get the lock gets a 409 with the code `import-in-progress` and retries. The existing duplicate 409 on `POST lift-records` keeps its own code.

    Workout drafts and timer runs in browser storage are keyed by the id, not the number, so they follow their macrocycle.

    `fromMacrocycleNum` today gives source + 1 and can reuse a number, so it now passes the allocated number to `updateMacrocycle`. `agent-tools.ts:68` finds the previous macrocycle by number - 1, which is correct again once numbers are dense. Whichever number the model asks for, it strips notes from `imported` and `legacy` rows and from a continued run's sets up to that row's `importedThrough` date, so imported notes don't bypass decision 11. Rejected: plain identifiers that never change, the original default, which leaves numbers out of date order. Also rejected: a chronological position shown on screen or in URLs over a fixed stored id, which rewrites nothing but leaves stored numbers and what's shown disagreeing. The owner chose stored numbers knowing the cost in rewriting, URLs and undo. Also rejected: negative numbers, which leak into URLs and record ids.
4. **A gap of more than 14 days between sessions suggests a new macrocycle.** Exactly 14 days doesn't. Every suggestion is editable before commit, and the Assign step is the review: there's no separate confirmation per break. The threshold is fixed at 14 days. Rejected: a hard rule, since the owner said breaks "usually" mean starting over. Also rejected for now: a per-user setting or a per-import control, which can be added if someone's history keeps needing corrections.
5. **A single-lift session inside a break is flagged for the user to decide.** A break here means a gap of more than 14 days when that session is left out. It sits outside every stretch with no boundary decided, and Continue stays blocked until the user files it with the earlier stretch, joins the stretches, makes it a non-cycle workout (decision 23), or leaves it out. The same four choices apply when the gaps on both sides are over 14 days. A file with many flags gets one action that keeps every break and files each of those sessions with its earlier stretch. Rejected: silently ending the gap, or silently ignoring the session.
6. **Position comes from completed workouts, not calendar weeks.** `segmentLiftHistory` takes the import date. Completed workouts are distinct file workout numbers when the file has them, and sessions otherwise, so a double-session day or a sheet dated by week can undercount, and the lifter can change the suggested status. A macrocycle past its expected length with workouts left is `overran`. Once all workouts are done, the next session starts a new macrocycle. A run that finishes every workout is `completed`, even if it finished late, and its dates show the lateness. A last stretch with workouts left is `abandoned` if its last session is more than 14 days before the import date, the same break rule as decision 4. Otherwise it's `overran` or, inside its expected length, `in-progress`, and decision 2 says when it can continue as current. A stretch the lifter joins past its program's length, or that mixes programs, gets no suggested status. Rejected: calendar-only position, which misreads an interrupted or slow run.
7. **`abandoned` applies when workouts remain and the next stretch is a restart or a different program.** A restart is any boundary between stretches of one program: a gap over 14 days, a file's workout number falling back to a lower one, or a boundary the lifter placed. A gap of 14 days or less with none of these is the same run resuming, not a restart. When `overran` and `abandoned` both fit, `abandoned` wins, because it says how the run ended, and the dates still show the overrun. Like every status, this is a suggestion the lifter reviews at Assign and can change. Rejected: marking a run abandoned after a fixed time alone, because what ends a slow run is what comes after it, not how long it took.
8. **If the file has macrocycle numbers, keep its groupings and flag any conflict with the dates.** A conflict is a gap of more than 14 days inside one file number, measured without any lone sessions. The file has already placed those sessions, so they aren't flagged under decision 5. The file's program and number decide what's grouped together, because numbers are per program, and decision 3 decides the number stored, so a number already in use isn't a conflict. Numbers in one program that share or interleave dates would overlap, so Assign flags them and blocks Continue until the lifter moves a boundary. An exported file is the exception: decision 14 allows stored overlaps, so its overlaps are flagged and don't block. Rejected: dates always win, which would override the lifter's own record silently.
9. **A stretch's program comes from the file, then the lifts, then the Source step.** The order is the file's `Program` column when it names a known program, then the smallest known program containing all the stretch's lifts, then the program picked at the Source step, which also settles a tie. `Program`, `macrocycleNum` and `workoutNum` become optional columns for assigned imports. A program switch is a change in that column between sessions or, with no column, a session with a lift outside the current program. Lift names can't show a switch to a program whose lifts are a subset of the current one (5/3/1's four lifts are inside both RPT and Leangains), so that takes a column, a break, or the lifter. A stretch is matched when all its lifts belong to a known program. Otherwise it's stored under the Source program and flagged unmatched. A file's workout numbers are kept. Without them, workouts are numbered in session order, and rows joining a stored run continue from its highest number. With no known length, the rules can't tell finished from unfinished, so Assign asks the user for the status. Rejected: an "unassigned" sentinel program, because `program` is a required string read everywhere. Also rejected: requiring a custom program first, which blocks import.
10. **Imports change current training maxes only through the existing split.** That's the row-level split that routes a one-rep-max test row to Training Maxes. It happens before segmentation, so those rows don't count as sessions. For assigned imports, a split row belongs to the program of the stretch covering its date, or else the Source program, and it's skipped and counted if it's older than that program's current max. Assign says how many rows would change a max. A run the lifter continues under decision 2 adds the one other path. Assign lists each of its lifts with the current max and the value computed from that run's records, and the lifter chooses keep or overwrite per lift, with keep as the default. The value comes from `updateMaxes`, which needs a max for every lift and throws without one, so a lift with no current max is seeded at zero, dated before the run. A lift that's still at zero has no computed value. A computed value lower than the current max is in `flagged` as `proposedWeight`, not in `maxes`, so Assign reads both. `updateMaxes` skips any set with an `occurrence`, so a second same-day workout doesn't count toward the value, which is acceptable for a suggestion the lifter can see and change. A lift with no current max has to take the computed value or one the lifter enters, because the schedule needs it. Undo restores any max this overwrote, as decision 2 says. Rejected: setting current training maxes automatically from the latest imported stretch, which would change the live plan from old data, so a light or injured stretch would silently lower it, and cross the deload non-goal.
11. **The LLM sees every set: date, lift name, set number, weight and reps.** Lift names come from the catalog, and custom lift names are replaced with placeholders, because they're free text. Alongside the sets it gets the rules' stretches and flags, and each known program's name and length. Custom program names are free text too, so they're replaced with placeholders. Notes are opt-in per import and off by default. A request carries at most 1,500 sets and 2,000 output tokens. That cap is an estimate of what fits a local model, and the comparison records actual prompt size against it. A file over the cap sends every set for the sessions around breaks, flags and unmatched stretches, and a date, lift names and top set for the rest. If that still doesn't fit, no request is made and the lifter is told. Rejected: summaries only, the original default, which is cheaper but hides patterns like a deload from the model. Also rejected: real custom lift names, and notes on by default, which send free text the lifter hasn't chosen to share.
12. **The LLM is off unless a provider is configured, and Assign asks per import with yes as the default.** `IMPORT_SUGGESTIONS_PROVIDER` has no default, so nothing is called when it's unset, unlike the planning agent's factory. The Assign response says whether suggestions are available and from which provider, which is how the client tells Off from Unavailable. Assign then asks once per import, showing the provider's name, what's sent and the notes choice, and that holds for a local model too. Yes is the prominent answer and the one that takes focus, but nothing is sent until the lifter gives it, and Continue doesn't need an answer. It runs through a separate request, so the rules result never waits on it, with a 60-second deadline, no retries, and an abort when the lifter leaves the step. A wizard run reuses its result per file and notes choice, and each user gets 10 requests per hour, counted in a new `import_suggestion_usage` table with row-level security, because production runs several instances. Suggestions are anchored to session dates and re-validated when they arrive. Invalid or out-of-date ones are dropped and counted. It's a new port with one structured call, not the planning agent's tool loop. Rejected: an LLM-first breakdown, running automatically when Assign opens, and calling the LLM at commit, which could return something different from what the user confirmed.

    |---|-----------------|------------------------|
    | 1 | `boundary` | Adds or removes a boundary at a session date |
    | 2 | `lone` | Answers a decision 5 flag |
    | 3 | `status` | Sets a stretch's status |

13. **Duplicate detection counts rows, without assigned numbers.** That covers assigned imports and, from piece 1, the two paths in decision 2 that take a number from a file. It compares the file with what's stored for the user, under any program, per `(date, lift, setNum)`, with lift names compared through `liftSpellings`, and adds only the rows beyond the stored count. Rows with identical weight and reps pair first, so the rows left over are the real extras. Re-importing the same file adds zero rows, even after the breakdown or a stretch's program changes, and doesn't move rows already stored. Two same-day workouts stay separate, because the second counts as an extra row and takes the highest stored `occurrence` for its key + 1, so the unique key holds, even after an out-of-order undo. An exact repeat within one file, with the same weight and reps, counts once and is reported as skipped, as it is today, unless the file's `Occurrence` column tells them apart, which export writes so two identical same-day workouts survive a round trip. A re-exported row whose weight or reps changed is left as stored, and Preview shows how many differ. A stretch whose rows are all duplicates creates no `macrocycle` row. `skipDuplicates` can't do this alone, because the unique key includes both numbers, so commits and number allocation take `pg_try_advisory_xact_lock` per user. A second writer gets a 409 at once and can retry, because waiting would spend a 30-second transaction budget that already includes the upload. The lookup uses the existing `(userId, lift, date)` index unless the query plan at the row limit shows it needs another. The owner asked for this operation to be idempotent by default, and decision 19 is how a lifter replaces rows instead. Rejected: updating changed rows automatically, which matches by position within a date, so a reordered sheet could overwrite the wrong set. Also rejected: relying on the existing unique key, under which a changed breakdown would write every set a second time. Also rejected: leaving out `setNum` or counting per program, which would merge sets or re-import them after a program change.
14. **A file that has grown extends what's stored.** New rows join a stored imported macrocycle when they're under its program, it has workouts left, and no boundary from decisions 4, 6 or 7 falls between them. They take its number and update its end date. Assign shows these as "N new workouts join macrocycle X", and a stretch with nothing new as already imported. New rows that overlap more than one stored macrocycle, or one under another program, form their own macrocycle, and Assign says the dates overlap. Undo recomputes rather than restores: undoing any batch removes that batch's rows, removes macrocycle rows left with no lift records except a live or non-cycle one, and recomputes dates and suggested status from the rows that remain, keeping a status the lifter chose. A batch keeps its macrocycle changes in a separate field from its lift-record keys. Rejected: always forming a second macrocycle, which splits one real run, and restoring a stored pre-image, which is wrong once a later batch has added rows.
15. **One file can target a different program per stretch.** Assign has a program control on each stretch, and history spanning programs is the point of this proposal. So the batch records program with each key, and undo and duplicate lookup work across programs. Old batches stay readable and undo as before. Rejected: one program per file, which leaves row 2's problem in place.
16. **Assign gets its data from a new `mode=assign` call.** It re-parses the file with Review's exclusions and overrides, then returns stretches, flags, rows with no date, and how many rows would change a training max. It also returns the continue offer with that program's live macrocycle and its set count, the per-lift maxes from decision 10, and the counts for each overwrite scope. A date range is an input to this call, so its counts follow the range the lifter enters. When the macrocycle and workout columns are unmapped, Review doesn't flag those fields, and existing-record lookup waits until Assign. Rows with no date can't be stored, so they're left out and counted rather than held by the wizard's incomplete-row gate, and the lifter can go back to Review to fix or exclude them. Changing anything at Review discards Assign's edits with a notice, the way `reviewEditsDiscarded` works today. The `mode=preview` response tells the wizard whether `IMPORT_ASSIGN_ENABLED` is on, so Map columns knows which columns to require. Rejected: returning stretches from `mode=preview`, which runs before Review and can't see its exclusions.
17. **`mode=dry-run` and commit take the confirmed breakdown as session dates in the request body.** The same body carries a continued run and its max choices (decisions 2 and 10) and an overwrite's scope and confirmed counts (decision 19). Row positions shift during commit, so dates are the stable key, and `excludeKeys` already travels this way. An exported file's breakdown uses its program and number pairs instead, because its macrocycles can overlap on a date (decision 8). Each re-parses the file and validates the breakdown against it, in place of the strict number checks in `resolveCommitRows`. A lone session the lifter left out travels as an excluded date, and one made a non-cycle workout travels as a non-cycle date. A date outside every stretch, or overlapping stretches, gets a 4xx naming the problem, and the wizard returns to Assign with a fresh result. Commit is all-or-nothing, and that includes the batch save, which is otherwise the only way to correct these rows. Rejected: row indexes, and calling the rules again at commit, which could drop the lifter's edits.
18. **Existing records get `macrocycle` rows through a backfill in piece 1.** There's one row per distinct user, program and number across `lift_record`, `macrocycle_dashboard` and the five other tables that hold a number, because a macrocycle can exist with no sets: starting the next one with nothing logged leaves its schedule and overrides behind. Dates come from its lift records. A number with no lift records and no dashboard takes its start date from its earliest scheduled date, or else the date of the next number down, and is stored as `legacy` with status `unknown`. The current number is `live` with status `in-progress`, and it takes its start date from `macrocycleDate`, so it works with zero records. `lift_record` has no origin column, so other numbers can't be told apart: they're `legacy` with status `unknown`, shown as "Status unknown" and not read-only. A number that already mixes imported and live rows stays mixed. [#1113](https://github.com/merickvaughn/lifting-logbook/issues/1113) found no import requests in 30 days, so few are expected.

    The backfill then renumbers each program by date, using the same rewrite as imports, so chronological order holds for all history from the start. It writes each macrocycle's old number to `macrocycle.backfillNumber` before changing anything, and a script reverses the rewrite from that column, including batch keys. The script is only safe until the next renumbering, because later macrocycles have no old number and a later rewrite can make old numbers collide. So it refuses to run if a macrocycle has no `backfillNumber` or the numbers have changed since the backfill. A live macrocycle's URL can change. Rejected: leaving numbers alone until the next import of older history, which is a safer migration, but order wouldn't be guaranteed at first. Also rejected: guessing origin from `ImportBatch`, whose rows are deleted on undo and may be missing.
19. **A lifter can overwrite with a fresh import.** Adding new rows is the default. Assign also offers Replace, with a chosen scope: all history, all imported history, or a date range. All history covers every lift record and macrocycle in every program, including live ones with their schedules and overrides. All imported history covers `imported` macrocycles and their records, plus non-cycle workouts that came from an import, which their batches' keys identify, and keeps ones recorded by hand. A date range covers records of any origin dated inside it, and a macrocycle at the range's edge is shortened, with dates and suggested status recomputed from what remains, and `macrocycleDate` moved if a live macrocycle's start is cut. A macrocycle left with no records is removed, including a live one with its schedule and overrides, and the counts say so. File rows outside the range follow decision 13. Training maxes are left alone apart from decisions 2 and 10. Assign counts what would be removed in each scope, and Preview makes the lifter confirm those counts. A commit whose confirmed counts no longer match is rejected. A backup is taken first (decision 21), and the batch records its snapshot. Undo removes the batch's rows and restores that snapshot. It's refused with a reason once the snapshot has expired or been deleted, because it would otherwise delete the new rows and restore nothing. It's also refused while a later overwrite exists, so overwrites undo newest first. Deleting a snapshot warns that it ends that undo. Rejected: a single fixed scope, because the owner wants to choose.
20. **Clear data removes training data and keeps setup.** It clears `lift_record`, `macrocycle`, `macrocycle_dashboard`, `training_max`, `training_max_history`, the three workout override tables, `focus_day_state`, `macrocycle_scheduled_workout` and `import_batch`. It keeps custom programs, custom lifts, lift metadata, lift modifications, body weight, strength goals, focus blocks, settings and the account. The action lives on a settings screen, takes a backup first, offers a download of all sets in decision 22's format, and asks the lifter to confirm the counts. Rejected: clearing everything except the account, which means rebuilding setup, and per-category checkboxes, where some combinations need their own rules, such as clearing custom lifts while records still use them.
21. **Backups are server snapshots kept for 30 days.** Overwrite and clear each store one snapshot row per action in a new `data_snapshot` table with row-level security forced: user, kind, scope, expiry and the affected rows as compressed JSON. The lifter can restore a snapshot, delete it now, or download its sets as a CSV in decision 22's format, with the same formula handling. Its maxes, schedules and overrides come back only through Restore.

    The API has no scheduler, and row-level security hides every row from a job with no user set, so it would delete nothing and report success. So a daily scheduled workflow executes a new Cloud Run job, the way the migrate job runs, under the migration role that row-level security doesn't filter. It only deletes rows past their expiry, logs how many, and fails if any expired rows remain. Any read treats an expired snapshot as gone, so a late job can't extend retention. The screen says that cleared data stays on the server until the snapshot expires or is deleted.

    Restore keeps anything stored since. A snapshot macrocycle whose stable id still exists takes its rows back. Otherwise it comes back as a new row with a temporary number, so its sets can't merge with a stored macrocycle holding the same number, and then the program renumbers. Sets skip duplicates through decision 13. What's stored now wins for rows there can only be one of: `macrocycle_dashboard` per program, and `training_max` per lift. The snapshot's come back only where none is stored, and a macrocycle whose pointer didn't come back is history, closed as in decision 1. If the snapshot can't be saved, the action fails and changes nothing. Rejected: keeping snapshots until deleted, because "clear" would never remove anything from the server and storage would grow without limit. Also rejected: a forced download with no server copy, because recovery would depend on the lifter keeping a file.
22. **Export is a CSV of sets the importer can read back.** Its columns are the existing lift-record headers, including `Program`, `Macrocycle #` and `Workout #`, plus `Occurrence`, `Modifications` and a new optional `Status`. A file with an `Occurrence` column is treated as an export, since a sheet has no reason to carry one. That turns off the 1RM split for it, which would otherwise divert any set whose note mentions "1rm" to Training Maxes, and it lets decision 8's overlaps through. The lifter can filter by program, macrocycle or date range. Re-uploading it keeps the groupings through decision 8, and a `Status` column counts as a status the lifter chose. `Modifications` holds that set's modification ids, and an id the account no longer has is dropped and counted. Training maxes and setup aren't included. In `Program`, `Lift` and `Notes`, a cell starting with `=`, `+`, `-`, `@`, a tab, a carriage return or a line feed gets a leading apostrophe, so a spreadsheet won't run it as a formula. The importer removes an apostrophe only when one of those follows it, so a note that really starts with an apostrophe stays as written. Past the importer's 5,000-row limit, the page lists parts, each under the limit and cut between macrocycles, which the lifter downloads one at a time and re-uploads oldest first. Origin doesn't survive a round trip, so a re-uploaded live macrocycle comes back as `imported`. [#947](https://github.com/merickvaughn/lifting-logbook/issues/947)'s whole-account download uses this same format and parts for its lift-record files, on the same settings screen, and whichever ships first builds the serializer and the screen. The owner chose one shared export over two formats. Rejected: making this filtered download a zip, which the importer would have to learn to read. The zip is #947's, for a whole-account copy. Also rejected: one CSV with a warning, which silently stops being re-uploadable, and raising the row limit, which conflicts with all-or-nothing commits and [#925](https://github.com/merickvaughn/lifting-logbook/issues/925).
23. **A non-cycle workout belongs to no program and no macrocycle.** It's for training outside any plan, like a session on vacation. Its sets are ordinary `lift_record` rows under a reserved program id, `non-cycle`, with one `macrocycle` row, number 1, origin `non-cycle` and status `unknown`, created on first use. Each workout takes the next `workoutNum` under the decision 13 lock, so two on one date stay separate, and it follows the same write rules as any macrocycle, including the stable id in decision 3. A custom program can't take the id, because custom program ids are UUIDs. The id stays out of the program list and the past-macrocycles list, and `POST switch` and macrocycle generation reject it. Training maxes are read and updated per real program, so these sets can't change one.

    The lifter starts one from History or the macrocycle page, chooses a date (today by default, never the future), picks lifts with the existing lift picker, and types weight and reps. Nothing is prescribed. Where a lift has a training max in the active program, the screen shows it for reference, with the previous max and the reps last performed at that weight, to give a sense of volume: "Training max 205 lb. Last at 200 lb: 8 reps." The previous max is the newest `training_max_history` entry for that lift and program whose weight differs from the current one. The reps come from the most recent set at exactly that weight, under any program, taking the lowest set number on that date. With no such set the line shows the max alone, and with no max it shows nothing. Sets can be edited, and a whole workout can be deleted through a new route, since no route deletes a lift record today.

    History adds these workouts whichever program is active, with no training max at the time, and they count toward personal records. A focus block summary already reads by lift and date across programs, so it counts them too. They really happened, so a heavy set on a non-cycle day should still register.

    Import reaches them in three ways: a lone session at Assign (decision 5), sets kept after an undo (decision 2), and any file row whose `Program` is `non-cycle`, which is stored as one and doesn't count as a session for segmentation. Decision 13 compares across programs, so re-importing a file adds nothing, whichever of these a row became. Export writes them with `Program` as `non-cycle`, so they round-trip, and they can be filtered like a program. Their parts are cut between workouts, because they have no macrocycle boundaries. Clear data, overwrite and restore treat them as they do any other rows.

    Rejected: storing them under the active program in a reserved number, which hides them from History after a program switch and puts them beside that program's max calculations. Decision 9's rejection of an "unassigned" sentinel doesn't apply, because that was a fallback for a file the importer couldn't match, and this is the lifter's own choice. Also rejected: a separate table, which needs a second path for logging, editing, History, records, duplicates, export and clear data. Also rejected: leaving these sets out of personal records, which would hide a real heaviest set, and showing no reference, because the owner wants the sense of volume.

### Comparison

- [ ] The pre-registration is frozen before either version's output is seen: the tracking issue's pre-registration comment is dated before the first generated result, and records prompt size against the model's `num_ctx`.
- [ ] A `/experiment-audit verdict` result is recorded before any decision on keeping the LLM version: [#1175](https://github.com/merickvaughn/lifting-logbook/issues/1175) links the engineering-journal file `sessions/lifting-logbook/reports/YYYY-MM-DD-macrocycle-assignment-comparison.md`, dated the day of the verdict, which contains it.

### Continue a run as current

- [ ] The offer appears only when it should: an API end-to-end test asserts `mode=assign` offers it on a last stretch with a known program, workouts left and a recent last session, and not on an older stretch, a finished run, an unmatched program or one over 14 days old.
- [ ] Continuing makes the run current: an API end-to-end test commits it and asserts the dashboard points at it with origin `live`, its program is active, the remaining workouts are scheduled from after the import date, completed workouts have no schedule, and a new set can be logged on it.
- [ ] A live macrocycle in that program isn't ended without agreement: `ImportWizard.test.tsx` asserts Continue is blocked until the lifter agrees, with the set count shown. An API end-to-end test asserts the commit is rejected without that agreement, and that with it the old macrocycle's row is closed and its sets remain.
- [ ] Each max is the lifter's choice: an API end-to-end test asserts a kept max is unchanged, an overwritten one takes the computed value, and a lift with no current max can't commit without a value. `ImportWizard.test.tsx` asserts keep is the default and that a lifter can enter a value.
- [ ] The computed values hold for the hard cases: unit tests assert a program with no maxes at all returns a value per lift rather than throwing, a lift with no qualifying set has no value, and a lower value comes from `flagged`. An API end-to-end test asserts `mode=assign` succeeds for a lifter with no maxes.
- [ ] A continued run's status can't contradict it: an API end-to-end test asserts the stored status is `in-progress`, and `ImportWizard.test.tsx` asserts the status control is locked while it's chosen.
- [ ] Undo reverses it: an API end-to-end test undoes a continued run with an ended macrocycle and an overwritten max, and asserts the pointer, active program, ended macrocycle's status, the max and the schedule are as they were, including after an older-history import renumbers the ended macrocycle.
- [ ] Undo keeps sets logged since the import: an API end-to-end test logs a set on the run, undoes it, and asserts the set remains as a non-cycle workout with its date, weight, reps, notes and modifications, the imported rows, the run's `macrocycle` row, schedule and overrides are gone, the pointer is back, and numbers follow date. History shows the workout, and the set can be edited.
- [ ] Undo refuses when it can't be safe: API end-to-end tests assert a refusal with a reason after the next macrocycle starts and after the run is deleted. A max changed since the import is skipped and flagged.

### Backups, clear data and export

- [ ] Clear data clears only what decision 20 lists: a `*.db.e2e.spec.ts` test seeds every table, clears, and asserts the listed tables are empty for that user, the kept ones are unchanged, and another user's rows are untouched, running as the restricted role.
- [ ] Clear and restore are a safe pair: API end-to-end tests clear, restore, and assert every row is back with numbers in date order.
- [ ] Restore keeps what's newer: an API end-to-end test clears, initializes the program again with new maxes, logs a set on macrocycle 1, restores, and asserts the two macrocycles stay separate, the new set, dashboard and maxes are unchanged, and the old macrocycle comes back as history.
- [ ] No backup means no change: a `*.db.e2e.spec.ts` test forces the snapshot save to fail and asserts nothing was cleared.
- [ ] Backups expire and can be deleted: API end-to-end tests assert a snapshot past its expiry can't be restored or downloaded even before the job runs, and that Delete removes it at once. Row-level security on `data_snapshot` holds under the restricted role.
- [ ] The expiry job deletes under its real role: a `*.db.e2e.spec.ts` test runs the job's script as the migration role and asserts expired rows of two users go, unexpired rows stay, and the count is logged. It also asserts the job fails if an expired row remains. `.github/workflows/` has the daily schedule, and `docs/deploy.md` names the job.
- [ ] A snapshot download holds its sets: an API end-to-end test downloads a snapshot and clear's offered download, and asserts each parses as decision 22's format with formula handling applied.
- [ ] Clear asks first: a Playwright test asserts the counts and the 30-day notice are shown, that nothing changes until confirmed, and that the confirm control is keyboard-operable.
- [ ] Export filters: an API end-to-end test asserts the rows returned for each of program, macrocycle and date range, and that another user's rows never appear.
- [ ] Export round-trips: an API end-to-end test exports all programs, clears, re-imports the file through `mode=assign` and commit, and asserts the same sets, groupings and statuses. Its fixture includes two identical same-day workouts, a set whose note mentions "1rm" (which stays a set and changes no max), a set with modifications, the same number in two programs, two overlapping macrocycles in one program, and a non-cycle workout. Re-importing without the clear adds zero rows.
- [ ] Large exports fit the importer: a test with over 5,000 rows asserts each part is under the limit, parts are cut between macrocycles, and uploading them oldest first restores everything.
- [ ] Spreadsheet formulas don't run: a test asserts a custom lift or note starting with each trigger character is exported with a leading apostrophe and re-imports without it, that a note really starting with an apostrophe is unchanged, and that a negative weight isn't touched.

### Overwrite with a fresh import

- [ ] Each scope removes what it says: API end-to-end tests overwrite with all history, all imported history and a date range, and assert the rows removed and kept. All imported history keeps `live` and `legacy` macrocycles and hand-recorded non-cycle workouts, and removes imported non-cycle workouts. A date range shortens a macrocycle at its edge and recomputes its dates, moves `macrocycleDate` when a live one's start is cut, and removes a live macrocycle wholly inside it, with its schedule and overrides.
- [ ] Overwrite asks first: `ImportWizard.test.tsx` asserts add is the default, that each scope shows its counts, and that Preview requires confirming them. An API end-to-end test asserts a commit whose confirmed counts no longer match is rejected.
- [ ] Overwrite can be undone: an API end-to-end test overwrites all history, including a live macrocycle with a schedule and overrides, undoes it, and asserts everything is as it was, with no snapshot left unrestored.
- [ ] Undo can't lose data once a backup is gone: API end-to-end tests assert undo is refused with a reason and the new rows stay, after the snapshot expires and after it's deleted. With overwrites A then B, undoing A is refused until B is undone, and undoing both in that order restores the original rows.
- [ ] No backup means no overwrite: a `*.db.e2e.spec.ts` test forces the snapshot save to fail and asserts nothing changed.

### Non-cycle workouts

- [ ] A workout can be recorded with no plan: a Playwright test starts one, picks a lift, enters a set, and asserts it's in History. An API end-to-end test asserts a future date gets a 4xx, and that two on one date stay separate.
- [ ] Training maxes can't change: an API end-to-end test records a set heavier than the current max, starts the next macrocycle, uses `fromMacrocycleNum`, and asserts the max and `training_max_history` are unchanged.
- [ ] The reserved id stays reserved: API end-to-end tests assert `POST switch` and macrocycle generation reject `non-cycle`, that it's missing from the program list, and that the past-macrocycles list leaves it out.
- [ ] History holds across a program switch: an API end-to-end test and a History page test record one under program A, switch to B, and assert it's still listed and counts toward that lift's personal record.
- [ ] The reference line reads as decision 23 says: a unit test asserts "Training max 205 lb. Last at 200 lb: 8 reps." for seeded data, the max alone with no set at the previous weight or no previous max, nothing with no max, the lifter's preferred unit, and the reps from the most recent date's lowest set number.
- [ ] Sets can be edited and a workout deleted: an API end-to-end test edits a set, deletes the workout, and asserts its rows are gone and the macrocycle row remains. It also asserts deleting a program's current macrocycle leaves non-cycle workouts alone.
- [ ] A hand-recorded set isn't imported twice: an API end-to-end test records a workout, imports a file holding the same sets, and asserts zero new rows, with the file's rows counted as duplicates.
- [ ] A `Program` value of `non-cycle` is honored: an API end-to-end test imports such a row in a sheet with no `Occurrence` column and asserts it's stored as a non-cycle workout, and that `segmentLiftHistory` doesn't count it as a session.
- [ ] Row-level security holds: a `*.db.e2e.spec.ts` test running as the restricted role asserts one user can't read, write or delete another user's non-cycle workouts.
- [ ] It works by keyboard and at phone width: a Playwright test records one with key presses only and asserts no horizontal page scroll at 375px.
- [ ] The docs follow: `docs/domain-model.md`, `docs/glossary.md` and `apps/web/lib/glossary.ts` each define a non-cycle workout.

## Out of Scope

- Adjusting training maxes or the plan automatically after a break (non-goal: deload and missed-session recovery). A lifter's own per-lift choice under decision 10 isn't automatic.
- Substitutions ([#1133](https://github.com/merickvaughn/lifting-logbook/issues/1133)). That issue also uses the word "assign", for a different thing: assigning lifts to what a program plans. This proposal assigns history to macrocycles.
- Mobile upload UI.
- A rest timer, plan or prescribed weights for a non-cycle workout.
- Choosing a production LLM provider ([#136](https://github.com/merickvaughn/lifting-logbook/issues/136) covers tier-aware provider selection).
- Recomputing training max history per macrocycle (`docs/domain-model.md`, D14).
- Showing imported macrocycles on live workout pages, apart from a run the lifter continues.
- Downloading training maxes and setup. The export covers sets and their macrocycles, and [#947](https://github.com/merickvaughn/lifting-logbook/issues/947) covers the whole account.
