## Production deploy

| Script | Purpose |
|---|---|
| [`bootstrap-gcp.sh`](bootstrap-gcp.sh) | One-time GCP bootstrap for a lifting-logbook deploy (prod or staging): creates the project, links billing, enables the APIs Terraform needs, and provisions the Terraform state bucket. Idempotent. Pass `--project-id lifting-logbook-staging` to bootstrap the staging environment. See [`docs/deploy-single-user.md`](../docs/deploy-single-user.md) and [`docs/staging-runbook.md`](../docs/staging-runbook.md). |
| [`bootstrap-otel-secrets.sh`](bootstrap-otel-secrets.sh) | One-time Grafana Cloud auth-header bootstrap for the OTel Collector (#474): prompts for the OTLP/Loki instance IDs + an API token (token prompt hidden), builds the `Basic base64(instanceId:token)` headers locally, and creates+populates the `lifting-logbook-{stg,prod}-otel-{otlp,loki}-auth-header` Secret Manager secrets the deploy pipeline reads. Idempotent (adds a new version on re-run); the secrets are **not** Terraform-managed. Pass `--env staging`/`--env production` to scope to one environment. See [`docs/deploy.md`](../docs/deploy.md#otel-collector--grafana-cloud-telemetry). |
| [`check-cloud-run-serving-revision.py`](check-cloud-run-serving-revision.py) | Deploy gate run as the last step of `.github/actions/deploy-cloud-run-otel-sidecar` (#1042): reads `gcloud run services describe --format=json` and fails unless the newest ready revision gets 100% of `status.traffic` — i.e. traffic is not pinned to an older revision. Deliberately checks nothing else, so a concurrent deploy to the shared staging services cannot fail it. Tests: [`test_check_cloud_run_serving_revision.py`](test_check_cloud_run_serving_revision.py) (calibrated on a live staging describe and the #1042 pin shape). Stdlib only. |
| [`check-served-version.sh`](check-served-version.sh) | Production smoke probe in `deploy.yml` (#1042): fails unless `GET /version` reports the commit the run deployed (`gitSha == github.sha`); takes an optional bearer token for the IAM-gated api. Proves *which* build answered, which `/readyz`, `/livez` and `/sign-in` cannot. Prod only — staging is redeployed by every PR. Tests: [`test_check_served_version.py`](test_check_served_version.py). |
| [`check-staging-deployed-image.py`](check-staging-deployed-image.py) | Gate run in `staging.yml` before the integration tests (#1208): reads `gcloud run services describe --format=json` for `lifting-logbook-stg-api` and `-web` and fails, with an `::error::` naming both images, unless each ingress container's image in `spec.template` is the one this run built (matched by tag, then by digest from Artifact Registry). Proves the staging lock held — that no other run redeployed staging after this one. It checks what was applied, not what serves; [`check-cloud-run-serving-revision.py`](check-cloud-run-serving-revision.py) covers serving. A failure to read the services is reported as that, not as another run's deploy. Tests: [`test_check_staging_deployed_image.py`](test_check_staging_deployed_image.py). Stdlib only. |
| [`deploy-prod-infra.sh`](deploy-prod-infra.sh) | Automates `terraform init` → workspace select → `apply` for the production environment. Maps custom domains and prints GitHub Actions secrets. Use `--plan-only` to preview. Run after `bootstrap-gcp.sh`. |
| [`fix-cicd-sa-iam.sh`](fix-cicd-sa-iam.sh) | One-time recovery for a project bootstrapped before `infra/terraform/main.tf` granted the CI/CD service account Owner (#302, #304): run once, as a project owner, when the Deploy workflow fails with a `403` / `setIamPolicy denied` / `storage.objects.list` error. Grants `<project>-cicd@<project>.iam.gserviceaccount.com` `roles/owner` on the project and `roles/storage.objectAdmin` on `gs://<project>-tfstate`, so `terraform apply` from CI can take over those bindings. Defaults to `lifting-logbook-prod`; `--project-id` selects another (for example `lifting-logbook-staging`). Exits without changing anything if there is no active `gcloud` account or the service account does not exist yet. Re-running is safe. See [`docs/deploy-single-user.md`](../docs/deploy-single-user.md) and [`docs/deploy.md`](../docs/deploy.md). |
| [`inject-otel-sidecar.py`](inject-otel-sidecar.py) | Builds the two-container Cloud Run manifest for the api (#768) **and** web (#804) services by deriving from the live service (`gcloud run services describe --format=export`): adds the `otel-collector` sidecar + config-secret volume, sets the ingress container's `OTEL_EXPORTER_OTLP_ENDPOINT`, and drops the unused `SYSTEM_DATABASE_URL`. The ingress container name is parameterized (`INGRESS_CONTAINER_NAME`, default `api`; the web deploy step passes `web`), and the image comes from `INGRESS_IMAGE`. The `deploy.yml` api/web deploy steps pipe its output to `gcloud run services replace`. An optional `INGRESS_EXTRA_ENV` (newline-separated `KEY=VALUE`) merges extra vars into the ingress env — the web deploy uses it for the #806/#809 same-origin guard (`CLIENT_ERROR_ALLOWED_ORIGINS` derived from the web service's own URL, plus `CLIENT_ERROR_DROP_CROSS_ORIGIN`). It also sets `spec.traffic` to 100% on the latest revision, so a manual `update-traffic --to-revisions` rollback pin does not survive a deploy (#1042). Idempotent; requires PyYAML. Tests: [`test_inject_otel_sidecar.py`](test_inject_otel_sidecar.py). |
| [`migrate-prod-db.sh`](migrate-prod-db.sh) | Applies all database migrations to the production Cloud SQL instance. Temporarily enables a public IP, runs Prisma migrations and the `user_data_source` infra migration via the Cloud SQL Auth Proxy, then removes the public IP. Downloads the proxy automatically. |
| [`migrate-staging-db.sh`](migrate-staging-db.sh) | Applies all database migrations to the staging Cloud SQL instance. Staging-specific variant of `migrate-prod-db.sh`: uses the shared `lifting-logbook-tfstate` state bucket (prefix `terraform/state`), the `-stg-` secret naming pattern, `PROXY_PORT=5434`, and forces `sslmode=disable` on the proxy URL for Prisma compatibility. |
| [`staging-env-lock.py`](staging-env-lock.py) | The staging environment lock (#1208, #1216, #1217, #1261): `acquire` / `release` of one GCS object, `ci-locks/staging-environment.json` in the `<staging project>-ci-locks` bucket, so a run's staging Terraform apply, deploy and integration tests are one critical section. Created with `ifGenerationMatch=0`; waiters poll and are never cancelled. A `merge_group` or `push` waiter keeps a fresh marker object while it waits, and a `pull_request` waiter does not take a free lock while another run's fresh marker exists. The lock records the holder's run id, so the same run can re-take it (a re-run of failed jobs) and `release` never deletes another run's lock. A lock is taken over when GitHub says its holder is done, or, when GitHub can't say, once it is older than `--stale-min` (40). `--timeout-min 0` never waits; `--holder-job` scopes a hold to one job; `--recreate-in-project` recreates a deleted lock bucket. Used by `staging.yml` and `deploy.yml`; needs `gcloud` auth and `GH_TOKEN`. Tests: [`test_staging_env_lock.py`](test_staging_env_lock.py), [`test_staging_terraform_under_lock.py`](test_staging_terraform_under_lock.py). Stdlib only. See CLAUDE.md "Staging overwritten mid-test". |
